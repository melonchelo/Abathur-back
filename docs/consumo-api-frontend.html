Abathur · cómo consumir la API

Guía para el frontend · base http://localhost:3000/api · 10/11/2026

Cada pantalla llama a un servicio que devuelve Observable<T>. El componente no arma la URL. Esta guía dice qué pide cada ruta, qué devuelve y qué ticket del backlog la usa. En el backlog los tickets de frontend son F- (no FE-). Los de backend son BE-.

1. Antes de la primera llamada

  • Levantar el back: npm run seed y después npm run dev en Abathur-back.
  • El token API_BASE_URL vale http://localhost:3000/api (F-04). Ningún servicio concatena el host a mano.
  • CORS ya acepta http://localhost:4200.
  • Salvo POST /auth/login, toda ruta pide Authorization: Bearer <token>. El interceptor de F-04 lo agrega.
  • El servidor vuelve a leer el rol en cada pedido. Ocultar un botón con appHasRole no alcanza: el mismo pedido hecho a mano responde 403 (F-34).
  • Identificadores y fechas son string. Las fechas vienen en ISO (2026-10-01T09:00:00.000Z) y se muestran con DatePipe y locale es-AR.
  • El JSON va en camelCase: weightAtVote, categoryId, underReview. No usar los nombres de columna de la base (weight_at_vote).
Errores. Toda falla responde { code: string; message: string } con un status HTTP. readApiError (F-05) es el único lugar que estrecha unknown. Mostrar message en la pantalla y ramificar con code cuando haga falta (credenciales, quórum, motivo obligatorio, HTML).

3. Sesión · BE-0 · F-07

POST /auth/login

públicoBE-0F-07

{ "username": "ana", "password": "abathur" }

// 200
{
  "token": "<jwt>",
  "user": { "id": "u-ana", "username": "ana", "alias": "Ana",
            "role": "cliente", "active": true, "reputation": 15,
            "createdAt": "2026-10-01T09:00:00.000Z" }
}

El JWT incluye role, username y el id en sub. Guardar el token y el usuario. No decodificar el rol para autorizar una escritura: el servidor lo ignora y mira la base.

  • 401 INVALID_CREDENTIALS: usuario o contraseña. Mostrarlo con @if.
  • 403 ACCOUNT_INACTIVE: la cuenta existe y la desactivaron. No entra.

GET /me

autenticadoBE-0F-07

Devuelve el mismo objeto User del login, con la reputación recalculada. Sirve para rehidratar la sesión al recargar. 401 TOKEN_MISSING, TOKEN_INVALID o ACCOUNT_INACTIVE mandan de vuelta a /ingreso.

4. Artículos · BE-0 y BE-1 · F-10 a F-15, F-26, F-31

interface ArticleSummary {
  id: string; title: string; summary: string; categoryId: string;
  currentVersionId: string; currentVersionNumber: number;
  createdBy: string; createdAt: string; updatedAt: string;
  underReview: boolean; // hay una propuesta que no está aceptada ni rechazada
}
interface ArticleVersion {
  id: string; articleId: string; versionNumber: number;
  title: string; summary: string; content: string; // Markdown, nunca HTML
  categoryId: string; tags: string[]; sources: { title: string; url: string }[];
  changeSummary: string; publishedBy: string; publishedByAlias: string;
  publishedAt: string; proposalId: string | null; isCurrent: boolean;
}
interface ArticleDetail extends ArticleSummary { currentVersion: ArticleVersion; }

GET /articles?q=&categoryId=

autenticadoBE-0F-10F-11F-14

Devuelve ArticleSummary[]. q busca en título y resumen, no en el cuerpo. categoryId es exacto: un click en el árbol manda el id de esa categoría, no el de las hijas. Conviene dejar ambos en los query params de la ruta para que recargar conserve la búsqueda.

GET /articles/:id

autenticadoBE-0F-12F-13F-31

Devuelve ArticleDetail. appAvisoRevision se prende con underReview. El cuerpo se parte en el cliente (#, ##, párrafo, lista con -) y se pinta con @switch, sin innerHTML. Después de aceptar una propuesta, volver a pedir este GET: la versión vigente cambia y el aviso se apaga cuando ya no quedan propuestas abiertas. 404 ARTICLE_NOT_FOUND.

GET /articles/:id/versions

autenticadoBE-0F-15F-31

Devuelve ArticleVersion[], de la más nueva a la más vieja. Destacar la que tiene isCurrent: true. Mostrar publishedByAlias, publishedAt y changeSummary.

GET /articles/:id/versions/:versionId

autenticadoBE-0F-19

Una versión puntual. El diff de una modificación compara content de esta versión (la de proposal.baseVersionId) contra proposal.proposed.content. 404 VERSION_NOT_FOUND.

POST /articles

adminBE-1F-26

{
  "title": "Cierre de caja",
  "summary": "Cómo cerrar la caja al final del turno.",
  "content": "# Cierre de caja\n\n- Contar el efectivo.\n",
  "categoryId": "c-caja",
  "tags": ["caja"],
  "sources": [{ "title": "Manual", "url": "https://example.com/manual" }],
  "changeSummary": "Versión inicial"
}

Responde 201 con ArticleDetail. Nace la versión 1 y currentVersionId apunta a ella. tags, sources y changeSummary pueden omitirse. El contenido se guarda igual a como llegó.

  • 403 ROLE_FORBIDDEN si no es admin.
  • 400 HTML_NOT_ALLOWED si content trae una etiqueta (<p>, <br/>, un comentario HTML). El validador del formulario tiene que avisarlo antes; el del servidor es el que vale.
  • 400 CATEGORY_NOT_FOUND o INVALID_FIELD.

  | 'controvertida' | 'aceptada' | 'rechazada';

interface Proposal {
  id: string;
  kind: 'creacion' | 'modificacion';

GET /proposals?status=&articleId=&authorId=

autenticadoBE-0F-16

Devuelve Proposal[], de la más nueva a la más vieja. El filtro de estado manda el literal (en_votacion, no el texto del pipe). El pipe estadoPropuesta solo traduce para mostrar.

GET /proposals/:id

autenticadoBE-0F-17F-28

El @switch del detalle tiene una rama por status. tally ya trae la suma de pesos y si hay quórum, para pintar el estado sin esperar al store. 404 PROPOSAL_NOT_FOUND.

POST /proposals

cliente o moderadorBE-1F-18

// Creación: no mandar articleId ni baseVersionId
{ "proposed": { "title": "...", "summary": "...", "content": "# ...\n",
                "categoryId": "c-caja", "tags": [], "sources": [] } }

// Modificación: los dos, y los dos juntos
{ "articleId": "a-apertura-caja", "baseVersionId": "v-apertura-caja-2",
  "proposed": { "...": "..." } }

Responde 201 con la propuesta en abierta. No toca el artículo publicado. El admin no puede proponer (403). Mandar solo uno de los dos ids responde 400 INVALID_PROPOSAL_TARGET. Una versión que no es de ese artículo responde 400 BASE_VERSION_MISMATCH. El mismo rechazo de HTML que en artículos aplica a proposed.content.

  "authorAlias": "Ana", "body": "...", "createdAt": "..." }

Comentario plano, sin hilos. El GET devuelve la lista en orden cronológico. Al crear, agregar a la lista el comentario que vuelve la API, sin recargar. El admin no comenta.

POST /proposals/:id/voting

moderador o adminBE-1F-21

Sin cuerpo. Pasa de abierta a en_votacion y devuelve la propuesta. Si ya no está abierta: 409 PROPOSAL_NOT_OPEN. El botón solo lo ven moderador y admin.

7. Votación · BE-2 · F-23, F-24

peso = min(5, max(1, Math.floor(reputacion / 10))). Reputación 10 → 1, 30 → 3, 50 o más → 5. La previa del store usa esta fórmula. El peso confirmado es weightAtVote del voto que devuelve el POST. Si el cliente manda un peso, el servidor lo ignora. 
interface Vote {
  id: string; proposalId: string; moderatorId: string; moderatorAlias: string;
  choice: 'a_favor' | 'en_contra';
  weightAtVote: number;  // congelado al votar
  createdAt: string;
}

GET /proposals/:id/votes

autenticadoBE-0F-17F-23

Carga inicial del VoteTallyStore. Reemplazar el arreglo del signal, no mutarlo. El quórum de la previa es votos.length >= 3, contando el borrador todavía no enviado.

POST /proposals/:id/votes

moderadorBE-2F-24

{ "choice": "a_favor" }

Solo con la propuesta en en_votacion. Responde 201 con el Vote. Reemplazar en el store el borrador por ese voto y dejar el draft en null. Un voto por moderador, y no se edita.

  • 409 ALREADY_VOTED
  • 409 PROPOSAL_NOT_IN_VOTING
  • 403 si es admin o cliente. El admin abre y cierra; no vota.

POST /proposals/:id/close

moderador o adminBE-2F-24

Sin cuerpo. Exige tres votos. Con quórum devuelve la propuesta en recomendada, desaconsejada o controvertida. El artículo publicado no cambia. Menos de tres votos: 409 QUORUM_NOT_MET y el estado sigue en_votacion. Mostrar ese error con @if. El botón de cierre se habilita con el computed de quórum, pero la cuenta que vale es la del servidor.

Ejemplos que tienen que coincidir con la spec del front: pesos 3, 3 y 1 con dos a favor dan 6 contra 1 y recomendada. Pesos 4, 2 y 2 con el 4 en contra empatan y quedan controvertida.

8. Decisión del administrador · BE-3 · F-28, F-30, F-31

POST /proposals/:id/decision

adminBE-3F-28F-30F-31

{ "outcome": "aceptar", "reason": null, "markBaseAsError": false }

outcome es aceptar o rechazar. reason puede ir vacío solo cuando la decisión acompaña un resultado con quórum (recomendada + aceptar, o desaconsejada + rechazar). Es obligatorio si se aparta, si hubo empate (controvertida) o si no hubo quórum. markBaseAsError solo tiene sentido al aceptar una modificación: le resta 5 a quien publicó la versión de base.

{
  "proposal": { "...status": "aceptada", "decision": {
      "outcome": "aceptar", "kind": "acorde", "reason": null,
      "markedBaseAsError": false, "decidedBy": "u-lucia",
      "decidedByAlias": "Lucía", "decidedAt": "...",
      "publishedArticleId": "a-apertura-caja",
      "publishedVersionId": "..." } },
  "article": { "...ArticleDetail de como quedó, o null si se rechazó" },
  "reputationEvents": [
    { "id": "...", "userId": "u-ana", "eventType": "aporte_respaldado",
      "sourceId": "p-recomendada", "delta": 5, "createdAt": "..." }
  ],
  "audit": { "id": "...", "action": "decision_propuesta",
             "decisionKind": "acorde", "reason": null, "...": "..." }
}
  • decision.kind es acorde, apartada o excepcional. La pantalla los distingue. excepcional es la resolución sin quórum.
  • Aceptar una creación hace nacer el artículo. Aceptar una modificación agrega una versión y no reescribe la anterior. Rechazar no cambia versiones ni reputación.
  • F-30 mete reputationEvents en el ReputationStore sin recargar y sin duplicar un evento que ya estaba. El autor suma aporte_respaldado (+5) una sola vez.
  • 400 REASON_REQUIRED cuando falta el motivo. El validador cruzado del formulario tiene que coincidir con esta regla.
  • 409 VOTING_NOT_CLOSED si ya hay tres votos y nadie cerró: primero POST .../close.
  • 409 PROPOSAL_ALREADY_DECIDED si ya estaba aceptada o rechazada.
  • 400 MARK_ERROR_NOT_ALLOWED si se marca error fuera de una modificación aceptada.

9. Personas, reputación y auditoría · BE-0 y BE-4 · F-29, F-32, F-33

interface ReputationEvent {
  id: string; userId: string;
  eventType: 'asignacion_inicial' | 'aporte_respaldado'
           | 'error_comprobado' | 'conducta_abusiva';
  sourceId: string; delta: number; createdAt: string;
}

GET /users y GET /users/:id

autenticadoBE-0F-32

Lista o ficha. reputation ya es la suma de los eventos. alias es el seudónimo visible.

GET /users/:id/reputation

autenticadoBE-0F-29

{ "userId": "u-ana", "score": 15, "weight": 1,
  "events": [ { "eventType": "asignacion_inicial", "delta": 10, "sourceId": "u-ana" },
              { "eventType": "aporte_respaldado", "delta": 5, "sourceId": "p-aceptada" } ] }

Carga el ReputationStore. El puntaje de la pantalla es el computed de la suma de delta, que tiene que coincidir con score. weight es el peso que tendría hoy un voto de esa persona.

POST /users

adminBE-4F-32

{ "alias": "Nora", "username": "nora", "role": "moderador",
  "initialReputation": 40 }

password es opcional; si no viene, la cuenta usa abathur. Responde 201 con el User y su reputación igual a initialReputation (evento asignacion_inicial, con sourceId igual al id de usuario). 409 USERNAME_TAKEN. El usuario solo admite letras, números, punto, guion y guion bajo.

PATCH /users/:id

adminBE-4F-32

{ "role": "cliente", "active": false, "reason": "Dejó el equipo" }

Hay que mandar role, active, o los dos. Desactivar no borra votos, eventos ni auditoría: el login posterior responde 403 ACCOUNT_INACTIVE y un token viejo deja de servir. 409 SELF_UPDATE_FORBIDDEN si el admin se modifica a sí mismo. 400 EMPTY_UPDATE si el cuerpo no cambia nada.

POST /users/:id/sanctions

adminBE-4F-32

{ "reason": "Insultos en un comentario" }

No es el módulo de sanciones del documento maestro: es solo el evento manual conducta_abusiva (−8). El motivo es obligatorio. Responde 201 con { user, audit, event }. El sourceId del evento es el id de esa auditoría, así que dos sanciones a la misma persona generan dos filas. Sumar event al store de reputación de esa persona. 409 SELF_SANCTION_FORBIDDEN si el admin se la aplica a sí mismo.

GET /audit?action=

adminBE-4F-33

interface AuditEntry {
  id: string; actorId: string; actorAlias: string;
  action: 'decision_propuesta' | 'alta_usuario' | 'cambio_usuario' | 'conducta_abusiva';
  entityType: 'proposal' | 'user'; entityId: string;
  reason: string | null;
  decisionKind: 'acorde' | 'apartada' | 'excepcional' | null;
  createdAt: string;
}

Lista de la más nueva a la más vieja. action filtra por uno de esos cuatro literales. En una decisión, decisionKind separa la excepcional de la acorde y de la apartada; en el resto de las acciones viene null. Mostrar actor, acción, entidad, motivo y fecha. Un cliente o moderador recibe 403.
